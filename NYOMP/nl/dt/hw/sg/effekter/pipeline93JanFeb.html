Distributed Graphics Library Errors and Cures

January/Febrary 1993 Issue of Pipeline

In the IRIS environment, network transparency allows for IRIS Graphics 
Library (GL) processes to be run on one IRIS workstation and displayed 
on another. In this way, the two systems may share work load in a client
-server relationship. This network transparency is based on the Distributed 
GL (DGL) protocol built into the shared GL.

The client application that is linked with shared GL is called the DGL 
client, while the graphics server is called the DGL server. The DGL 
client transmits graphics information over the TCP/IP Network where the 
DGL server receives and decodes this information into graphics commands 
to be sent down the graphics pipeline.

Many pitfalls exist, however, in using DGL effectively in the convoluted 
world of X and UNIX. To follow are some common DGL errors and fixes.

Setting $DISPLAY


For the purpose of the following illustrations, assume the DGL client machine
on which the IRIS GL program is being run is called client.sgi.com, and the 
local DGL graphics server machine is called serv.sgi.com.

The environment variable $DISPLAY must be set before an IRIS GL program 
can be run on a remote workstation and displayed on the local machine 
across the network. To be sure that $DISPLAY is set correctly, upon rlogin 
or telnet into client.sgi.com (the remote machine), type:

% env

Many environment variables will be shown; look for:
DISPLAY=somevalue 

If :0 is the current value of $DISPLAY, the program will be displayed on 
the remote-host, client.sgi.com, rather than on the local host, serv.sgi.com.

To set it correctly, type:
% setenv DISPLAY serv.sgi.com:0
Anytime the hostname is incorrect or not available in the host table, Network
Information Service (NIS), formerly called YP, or Domain Name System (DNS), 
the following error message will be displayed:
dgl error (gethostbyname): can't get addr for serv.sgi.com
dgl error (default init): default dglopen(serv.sgi.com:0,4) returned -1

Next, verify that you cannot get an IP address for the host:
# ping -c1 system
If no IP address is shown, none is available using the host lookup method 
in use on this system (NIS, DNS or /etc/hosts).
This error message can also be caused if you are using NIS, and the program 
was not linked with -lsun.

Setting xhost


xhost provides a way of granting or refusing permission for other clients 
to display on the local display. See the manual pages for xhost on permission 
to display. If xhost on serv.sgi.com is set not to allow other hosts to 
display on it, the following error messages are given when this request is 
made:
Xlib: connection to "serv.sgi.com:0.0" refused by server
Xlib: Client is not authorized to connect to Server
dgl error (access): dgl server access denied - serv.sgi.com:0
dgl error (default init): default dglopen(serv.sgi.com:0,4) returned -13
To grant permission to display on the local display server, type: 
% xhost + 
or 
% xhost + client.sgi.com
To grant permission permanently, add either of the above commands to 
$HOME/.xsession or /usr/lib/X11/xdm/xsesson

DGL Compatibility Between 3.x and 4.0.x

It is not possible to display an IRIS GL program running on IRIX 4.0.x onto 
a machine running IRIX 3.x. Assume for the following example that the DGL 
graphics display server is serv.sgi.com running IRIX 3.3, and client.sgi.com 
is the DGL client running 4.0.x.

The following error message will be given when you attempt to display IRIS 
GL on the local display server (serv.sgi.com):
dgl error (default init): can't talk to dgld on serv.sgi.com:0
or
dgl error (TCP connect): Connection refused
dgl error (default init): default dglopen(serv.sgi.com:0,4) returned
To display an IRIS GL program running on 3.x onto a machine running 4.0.x 
where the 3.x machine is now the DGL client and the 4.0.x machine is the 
DGL graphics display server, the IRIS GL program must be compiled with -ldgl 
rather than with -lgl_s. If you wish to use NIS, link with the Sun library 
-lsun as well.

DGL Error from services and inetd


When upgrading from 3.x to 4.0.x, the files /etc/services and 
/usr/etc/inetd.conf may not be updated properly. In these files, the DGL 
entry may be commented out for various reasons. Also, if you are running 
NIS and providing a services map, the Silicon Graphics-specific entries in
/etc/services on the Silicon Graphics system must be incorporated into the 
services map coming from the NIS master server. The following error message 
is associated with this problem:
dgl error (TCP connect): Connection refused
dgl error (default init): default
dglopen(serv.sgi.com:0,4) returned -127

If you are not using NIS and see the following entry in /etc/services;
#sgi-dgl        5232/tcp        # SGI Distributed Graphics Lib
delete the "#" character in front of sgi-dgl. Furthermore, if the following 
is in the /usr/etc/inetd.conf file;
#sgi-dgl stream tcp nowait root /usr/etc/dgld dgld-IM -tDGLTSOCKET
delete the # character in front of sgi-dgl. In order to reflect these changes 
to the networking daemon, type the following (in Super-User mode): 
# /etc/killall 1 inetd 
or 
# /etc/killall -HUP inetd
If NIS (especially with a non-Silicon Graphics system as NIS master) is 
being used, you will probably need to incorporate the Silicon Graphics-
specific services from /etc/services on the Silicon Graphics system into 
the services map provided by NIS.
To see if these services are already in the NIS, type the following command:
% ypwhich
overlord.sgi.com
(This is the NIS server that is providing service to your system.)
% ypmatch -x
Use "passwd" for map "passwd.byname"
Use "group" for map "group.byname"
Use "networks" for map "networks.byaddr"
Use "hosts" for map "hosts.byname"
Use "protocols" for map "protocols.bynumber"
Use "services" for map "services.byname"
Use "rpc" for map "rpc.bynumber"
Use "aliases" for map "mail.aliases"
Use "ethers" for map "ethers.byname"
(These are the various maps provided by NIS; note the services map.)
% ypcat services | grep sgi
sgi-bz 5132/udp
sgi-dgl 5232/tcp
sgi-arena 5131/udp
sgi-dogfight 5130/udp
sgi-bznet 5133/udp
(Here the required sgi-dgl service is registered and provided by the NIS 
service.)
If NIS is not providing the sgi-dgl service, coordinate with your local 
network administrator to have this included in the services map.

Running IRIS GL between Silicon Graphics and non-Silicon Graphics Machines

Many IRIS GL users want to display a GL program onto a non-Silicon Graphics 
machine such as HP, DEC, Sun, NCD X-Terminals, PC X-Terminals or any platform
able to rlogin, telnet or rsh to the Silicon Graphics machine. This is not 
possible with the current implementation of the IRIS GL. The following error 
messages are associated with this problem:
dgl error (TCP connect): Connection refused
dgl error (default init): default dglopen(serv.sgi.com:0,4) returned -127
or
Xlib: connection to "serv.sgi.com:0.0" refused by server
Xlib: Client is not authorized to connect to Server
dgl error (access): dgl server access denied serv.sgi.com:0.0
dgl error (default init): default dglopen(guest@serv.sgi.com,4) returned -13

Often times, users do not realize they are invoking IRIS GL programs when 
they connect a Silicon Graphics machine with a non-Silicon Graphics machine. 
They may try to invoke a program not knowing that it is a GL program (such as
System Manager, GL Demos, Buttonfly, WorkSpace, blanktime, Jot, Inventor, 
Explorer, mousewarp, dialwarp, etc), or have a GL or GL/X Mixed Model program 
invoked by startup scripts.

For the latter, many users attempt to run seemingly innocent programs upon 
startup or login such as blanktime or WorkSpace so these are invoked in 
either $HOME/.cshrc, $HOME/.login or even the system startup /etc/cshrc. 
The solution is to simply remove these statements from the startup files.

Crimson Server DGL Bug


If you have a Crimson Server running IRIX 4.0.4 or earlier, and have 
consistently gotten one of the previously mentioned errors, and it does not 
fall into any of the above DGL scenarios, you may have a known bug, which 
was fixed in the 4.0.5 release.

Error Messages May Vary


Some of the above error messages may vary from case to case. If your error
messages are slightly different from those listed, it is possible that the 
cures apply.

The errors and cures discussed in this article are a reflection of the most 
commonly made mistakes when using DGL in the IRIS environment. When you 
suspect a problem is DGL related, make sure you've browsed through all the 
scenarios before seeking further assistance.

For more information on network transparency and DGL, see Chapter 19 of the 
Graphics Library Programming Guide.
